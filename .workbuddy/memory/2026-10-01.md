## 第二十七次：喜欢下载/同步"解析正常、下载失败"根因与修复

**现象**：用户反馈"我的喜欢下载和同步报错，解析获取正常，就是下载失败"。
（最新 job `task-1790829921369-8eq06` 是 slides 图文分享链 is_slides=1，awemeId=7690781332884397923）

**根因（读 main.log 实证 + 网上查证，已更正此前"抖音全面收紧"的误判）**：
- ⚠️ 更正：此前把"页面通道 403"说成"抖音 10-01 全面收紧"是过度推断、证据不足。
  真实情况：抖音 Argus 门禁是 2026-08/09 就有的**老平台策略**，只针对**非浏览器直连请求**（CLI
  直连 API）；真实浏览器页面加载不受影响（见 MediaCrawler / douyin-downloader 社区资料）。
  这也解释了用户"解析正常"——CDP 真实页面能加载、能拿 id。
- 日志数据：9-28/9-29/9-30 页面通道（browser-fetch）分别成功 147/2481/3143 次（仅零星 5~24 次
  403，属正常重试）；**10-01 当天 0 次成功、923 次 403，且全挤在 05:xx 一次自动同步任务的反复重试里**。
  这更像那次会话/cookie/uifid 状态异常，而非平台级突变（9-30 还完全正常）。
- 10-01 那次 403 的是 `bridgeFetchWindow` 注入的 XHR/fetch（页面通道），不是页面自身加载。
  CDP 浏览器采集（页面自身加载 + DOM 兜底）仍能拿 id（用户侧"解析正常"）。
- **真正失败环节**：`collectUserWorksViaBrowser` 是"先 loadURL（首屏等4s）→ 再 attach → enable"，
  首屏接口（aweme/favorite）在 attach 前已发出、被 CDP 错过 → 只拿到 DOM 兜底的空 id
  （`{awemeId}`，无 play_addr / image_post_info）→ 下载阶段取不到播放/图集地址 → 失败。
- 单作品 slides 直链下载（video_downloader）仍走 get_video_detail（已 403），暂无完整源。

**修复（仅 main.js）**：
- `collectUserWorksViaBrowser` 在 `Network.enable` 成功后增加 `win.webContents.reload()`
  （+等 4.5s）**重放首屏请求**，让 CDP 在监听下截获完整 `aweme_list`（含 video.play_addr /
  image_post_info）。下载/同步直接复用该完整 aweme，不再依赖 403 的 detail 接口。
  日志新增 `[bridge] collect 已 reload 重放首屏请求（kind=...）`。
- 备注：reload 后 debugger session 仍 attached、Network.enable 保持，CDP 拦截持续生效。

**排查附带结论**：
- 下载 headers 已含 Referer(=>douyin.com/)、Origin、User-Agent（downloader_base._download_headers），
  抖音 CDN 防盗链不是本次问题。
- `browser-collect` 返回 `{ok, aweme_ids, items, stats}`，后端 `_browser_post_aweme_items` 存完整
  aweme；sync/user_downloader 回补优先复用，缺项才补详情。

**验证**：`node --check main.js` SYNTAX_OK。
**生效前提**：彻底退出托盘重开。
**验收**：日志出现 `collect 已 reload 重放首屏请求`；喜欢批量下载/同步应能拿到地址完成下载。
**限制**：若软件内登录 session 也过期（页面自身加载也被 403），reload 同样抓不到，需先确认登录态有效。

## 第二十九次："重开后喜欢同步还是失败" 根因定位（16:00 重启后）

**用户反馈**："重开还是不行，仔细看看什么问题"。

**定位过程（读 userData 真实日志 `C:\Users\USER-PC\AppData\Roaming\DRaccoon\logs\`）**：
- 此前一直误以为日志在 `E:\DRaccoon\main.log`（实际不存在）；真实 `main.log` 在 userData `logs\` 下，
  2.4MB，`main.js` 通过 `app.getPath('logs')` 写入（main.js:424）。
- 16:20 / 16:32 的 `sync-likes-*.stdout.log` 显示：`status_code=-502`、`page_size=0`、
  `sync_error: 获取喜欢列表失败：-502`，stderr 仅 `SyncService likes browser fallback recovered=0`。
- `-502 = STATUS_PAGE_BRIDGE_ERROR`（页内桥连不上）。
- **`main.log` 共 19968 行，最后一行停在 `08:36:16`，之后完全无内容**——没有 16:00 的
  `桥接服务已启动 port=...`（对比 08:31 有）。
- 当前进程列表（`tasklist`）只有 2 个 `node.exe`，**没有 `DRaccoon.exe` / `electron.exe`**。

**根因（确凿）**：16:00 的"重启"**根本没有真正启动/重启 DRaccoon 桌面端（Electron 主进程）**。
桌面端负责启动本地桥服务并把 `DOUZY_BRIDGE_PORT` / `DOUZY_BRIDGE_TOKEN` 注入后端 dispatcher 子进程
（main.js:415-416、691-700）。桌面端没跑 → 后端 `DOUZY_BRIDGE_PORT` 为空 →
`api_client._collect_via_electron_bridge` 静默 `return None`（1796 行）→ 喜欢兜底 `recovered=0`；
同时页内桥 `get_user_like`（aweme/favorite）连不上 → `-502`。
喜欢列表被 Argus 门禁，只能靠桌面端自带 Chromium 窗口（CDP 拦截）采集；**桌面端一关，必然 -502 + recovered=0**。
（8:32 那次成功，正是因为当时桌面端开着。）

**修复（改 2 个 Python 文件，已 `py_compile` 通过）**：
- `api_client.py`：`_collect_via_electron_bridge` 桥端口缺失时改**明确 logger.warning**（不再静默）；
  新增 `is_bridge_available()` 方法。
- `sync_service.py`：喜欢同步在桥不可用时（`is_bridge_available()` 为 False）直接 emit 可操作报错
  "获取失败：桌面端桥接不可用。请先打开 DRaccoon 桌面端并保持抖音登录，然后在桌面端内触发同步"，
  不再抛晦涩的 `-502`。

**给用户的修复动作（关键）**：喜欢同步/下载必须从**已登录抖音的 DRaccoon 桌面端内部触发**；
不要单独跑 dispatcher 后端，也不要在桌面端关闭/未登录时同步。验证方法：触发同步前看右下角托盘图标在不在、
`tasklist` 有没有 `DRaccoon.exe`；同步后 `main.log` 应出现 `桥接服务已启动` 与
`collect 已 reload 重放首屏请求（kind=like）`。
