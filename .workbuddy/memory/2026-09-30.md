# 2026-09-30

## 各 Tab（新发布/收藏/喜欢）与单作品/批量下载全部下不动 —— 根因与修复

**现象**：作者主页下载已恢复，但「新发布」「我的收藏」「我的喜欢」里点下载，
以及单作品下载 / 批量下载依旧失败。用户质疑"难道没改成和作者页面解析下载一样的逻辑吗"。

**根因（日志铁证 main.log）**：
`grep browser-detail main.log` → **37 次只有 1 次 ok=true**，其余全是
`error=未能从页面或接口获取作品详情`。
- 单作品/批量下载走 `core/video_downloader.py:31 get_video_detail()`；
- 新发布 / 喜欢 / 收藏里点下载，最终也都是逐条 `get_video_detail()`；
- `get_video_detail()` 在桌面端**完全依赖** Electron 桥 `/v1/browser-detail`；
- 而 `collectAwemeDetailViaBrowser()` 用的是 `show: false` 隐藏窗口 →
  Chromium 判定不可见 → **页面根本不渲染**（JS 不执行、接口不发、React 水合数据没有）
  → 必然取不到详情。这与作者页采集早已踩过并修掉的坑完全同一个。

**修复一（main.js，关键）**：`collectAwemeDetailViaBrowser` 改为与
`collectUserWorksViaBrowser` 完全一致的「屏幕外渲染」：
`show: true` + `x/y=-32000` + `skipTaskbar` + `setOpacity(0)` + `setAudioMuted(true)`；
仍取不到时用可见窗口自动重试一次（`forceVisible` / `_visibleRetry`）。

**修复二（main.js）**：`collectUserWorksViaBrowser` 支持全部 Tab 的 CDP 采集：
新增 `KIND_COLLECT_CONFIG`（post / like / collect / collectmix / mix / music），
每个 kind 配候选页面参数（`?from_tab_name=xxx` / `?showTab=xxx`）与优先接口；
接口匹配改为 `matchesApi()`：精确过滤 + **兜底「任意 /aweme/v1/web/ 响应带 aweme_list」**
（排除 feed/search），应对抖音频繁换接口路径（实测 music/list 404、mix/aweme 403）；
同一 kind 多候选页由末尾递归 `tabIndex+1` 逐个尝试。

**修复三（backend）**：
- `core/api_client.py`：新增通用 `collect_user_ids_via_browser(kind=...)`。
- `core/user_downloader.py`：抽出通用 `_recover_user_mode_with_browser(mode, ...)`，
  并新增 `_recover_user_{collect,mix,music,collectmix}_with_browser`。
  （自身账号模式 sec_uid 可能为 `self`，跳过作者一致性校验。）
- `core/user_modes/collect_strategy.py` / `collect_mix_strategy.py`：
  列表为空时调用基类 `_try_browser_recovery()` 走 CDP 兜底（原来完全没有兜底）。
- mix / music 本就走基类 `_collect_paged_aweme`，自动命中新增兜底。

**验证**：`node --check main.js` 通过；`py_compile` 通过；`pytest backend/tests` 9 passed；
运行时校验 UserDownloader 六个模式的 recover 方法均已挂载。

**生效前提**：彻底退出 DRaccoon 托盘进程后重开。

## 第二轮（02:05）：喜欢下载仍失败 + 采集窗口总是弹可见窗口

**用户反馈**：喜欢里点下载仍失败（aweme 7690661260433555802 获取作品详情失败）；
且每次都弹出可见的抖音窗口，弹了照样失败。

**探针实证（Playwright + 系统浏览器，脚本已删）**：
- 视频页**确实会发** `/aweme/v1/web/aweme/detail/`（200、响应含 aweme_detail，共 3 次）；
- 但全部发生在页面首次渲染时 —— Electron 在 loadURL 之后才能 attach CDP，**永远错过**；
- 页面水合数据里**没有**完整 aweme 对象：`_ROUTER_DATA` undefined、`__pace_f`(9块) 找不到、
  `RENDER_DATA` 找不到（只有 app 全局配置命中 id）；
- reload 后 detail 接口重放，全部可捕获 → **修法 = attach 后立刻 reload**。

**修复（main.js）**：
1. `collectAwemeDetailViaBrowser`：attach + Network.enable 后立刻 `webContents.reload()`，
   让详情请求在 CDP 监听下重放；轮询窗口 12s→15s；CDP 解析同时接受 `aweme_detail` 与
   `item_list[0]`；捕获时打日志 `detail CDP 捕获 aweme/detail 响应`。
2. 失败重试分级：先静默重建窗口重试一次（`_silentRetry`），仍失败才弹可见窗口
   （`forceVisible`）—— 尽量不打扰用户。
3. `collectUserWorksViaBrowser` 采集窗口**一律静默**（屏幕外渲染），
   只有 env `DOUZY_SHOW_COLLECT_WINDOW=1` 才可见 —— 用户反馈"总是弹浏览器"。

**弹窗根因**：`browser_fallback.headless` 默认 `False`（可见窗口），
且用户 `settings.json` 里 `browserFallback.headless=false`。
已改：default_config.py 与全部读取点默认 True；用户 settings.json 已备份
（settings.json.bak-headless）并把 `browserFallback.headless` 改为 true。

**修复（backend）**：
- `sync_service.sync_likes`：喜欢列表接口被 Argus 拒绝（实测 -502）时，
  先走 `_recover_likes_via_browser()`（CDP 采集 + 缺失逐条补详情）再报错。
- `collect_user_ids_via_browser` / 各 recover 默认 headless=True。

**验证**：`node --check` 通过；`pytest backend/tests` 9 passed。

**生效前提**：彻底退出托盘重开。

## 第二十六次：详情获取去窗口化（批量页内通道）

**用户诉求**："每个视频都得用浏览器获取吗？！！参考 douyin-downloader-main11111 源码改！"
—— 反对"每个作品新开一个 Chromium 窗口抓 aweme/detail"（20s/条、频繁失败、弹窗）。

**关键实证（main.log）**：页面通道（页内 XHR）对列表接口早已可用：
- `aweme/post/` 200，单页 1.19MB（18:26:32 起连续 14 页）
- `aweme/favorite/` 200，单页 50~60 万字节（18:18:19 起）
→ 说明签名/门禁在页内请求下可绕过，**详情同样不必开窗口**（此前
`_request_json_gated` 对 `/aweme/v1/web/aweme/detail/` 特判走开窗口，是性能瓶颈根因）。

**改造（Electron main.js）**：
- 新增 `/v1/browser-fetch-batch` 端点（**必须排在 `/v1/browser-fetch` 分支之前**，
  否则被 startsWith 吞掉）：一次窗口内页内并发 XHR（默认并发 5，上限 8）请求 N 个
  签名 URL，返回 `{ok, results:{key:{status,text}}}`。
- 新增 `fetchBatchViaPageBridge(items, signUa, concurrency)`：工作队列 + Promise.all，
  页面 crash 时销毁重建一次；未返回的 key 补 `{status:0,text:''}`；日志
  `[bridge] browser-fetch-batch total=N ok=M`。

**改造（backend api_client.py）**：
- `get_video_detail` 优先级改为：① 页内 XHR 通道（秒级、无窗口）② 开 Chromium 窗口
  （仅 allow_window=True）③ 直连（仅无 bridge 的 CLI）。新增参数
  `allow_window: bool = True`。
- 抽出 `_get_detail_direct`（原直连循环）、新增 `_get_detail_via_page_bridge`
  （aid 候选 6383→1128，兼容 aweme_detail / item_list[0]）、`_extract_aweme_detail`、
  `get_video_details_batch(ids, concurrency=5, chunk_size=30)`、`_post_bridge_json`。
- `_request_json_gated` 的 detail 分支：页内优先，失败才开窗口。

**改造（调用方批量化）**：
- `user_downloader` 新增 `_batch_fetch_details()`；post/like/通用 mode 三个回补循环
  改为「先批量预取，再逐条兜底」，且兜底传 `allow_window=False`（批量场景永不弹窗）。
- `sync_service._recover_likes_via_browser` 同样批量预取 + allow_window=False。
- 单作品下载（video_downloader）保持 allow_window=True 兜底。

**验证**：`node --check main.js` OK；新增
`backend/tests/test_detail_page_channel.py`（5 例：页内优先不窗口、批量不窗口、
批量端点、失败补单条、item_list 解析）；`pytest ../backend/tests` **14 passed**。

**生效前提**：彻底退出托盘进程重开。
**验收关键字**：日志出现 `browser-fetch-batch total=N ok=M` / `批量详情：请求 N 条，成功 M 条`。
